# Event Bus

> **In-process domain event pub/sub with glob-pattern subscriptions, priority-ordered sequential execution, error isolation, and event logging to Postgres.** Phase 1 foundation. Blocks workflows, audit, and integrations. Scaling path: in-process today, Cloud Pub/Sub for cross-service later.

---

## Overview

Every write to a domain table in Postgres fires a domain event. The event bus routes that event to subscribed handlers using glob-style pattern matching (`guest.created`, `guest.*`, `*.created`, `*`). Handlers execute sequentially by priority (lower number = first). A failing handler does not block subsequent handlers. Every emission is logged to the `event_log` table with full execution details (which workflows triggered, which actions succeeded or failed). The bus is the central nervous system of the platform -- workflows, cascades, audit trails, and external integrations all hang off it.

**Source files:**
- `functions/src/events/types.ts` -- DomainEvent, EventSubscription, EventLogEntry interfaces, EventAction union
- `functions/src/events/bus.ts` -- subscribe(), emit(), createDomainEvent(), pattern matching, event logging

## 1. Event Model

### Purpose

Define the canonical shape of every domain event so that any handler can react without re-querying. Events carry before/after values, the actor, and enough context to drive downstream logic.

### Detail

The `DomainEvent` interface (`types.ts`) carries:

| Field | Type | Description |
|-------|------|-------------|
| `eventId` | `string` | UUID v4, generated by `generateEventId()` via `crypto.randomUUID()` |
| `eventName` | `string` | Dot-separated concept + action, e.g. `guest.created`, `schedule.updated` |
| `domain` | `string` | Concept key, e.g. `guest`, `schedule`, `convention` |
| `action` | `EventAction` | Union: `created`, `updated`, `deleted`, `synced`, `external_created`, `external_updated`, `intake_received`, `completed`, `overdue`, `staffing_complete` |
| `recordId` | `string` | Primary key (Postgres row ID) of the affected record |
| `changedFields` | `ReadonlyArray<string>` | Optional. List of field names that changed (present on updates) |
| `previousValues` | `Record<string, unknown>` | Optional. Field values before the write |
| `newValues` | `Record<string, unknown>` | Optional. Field values after the write |
| `triggeredBy` | `string` | User email or `"system"` |
| `timestamp` | `string` | ISO 8601, set by `createDomainEvent()` |
| `metadata` | `Record<string, unknown>` | Optional. Arbitrary context (e.g. source integration, batch ID) |

The `createDomainEvent()` helper (`bus.ts:130-138`) accepts all fields except `eventId` and `timestamp`, which it generates automatically:

```ts
export function createDomainEvent(
  params: Omit<DomainEvent, "eventId" | "timestamp">
): DomainEvent {
  return {
    ...params,
    eventId: generateEventId(),
    timestamp: new Date().toISOString(),
  };
}
```

### Acceptance Criteria

- [ ] `createDomainEvent()` returns a valid `DomainEvent` with a UUID `eventId` and ISO 8601 `timestamp`.
- [ ] `eventName` always matches the pattern `{domain}.{action}`.
- [ ] `changedFields`, `previousValues`, and `newValues` are populated on update events; omitted on create/delete.
- [ ] All `DomainEvent` fields are `readonly` -- events are immutable after creation.
- [ ] `EventAction` union covers all platform lifecycle actions. New actions require a type update.

## 2. Subscription Model

### Purpose

Let any module register interest in domain events using intuitive glob patterns, with priority control over execution order.

### Detail

`subscribe()` (`bus.ts:33-52`) takes three arguments:

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `pattern` | `string` | -- | Glob pattern for matching event names |
| `handler` | `EventHandler` | -- | `(event: DomainEvent) => Promise<void>` |
| `priority` | `number` | `100` | Lower = runs first |

**Pattern syntax:**

| Pattern | Matches | Use case |
|---------|---------|----------|
| `guest.created` | Exact match only | Single-event handler |
| `guest.*` | Any action on `guest` concept | Concept-level reactor (audit, cache invalidation) |
| `*.created` | Any concept's `created` action | Cross-cutting concerns (welcome emails, default assignments) |
| `*` | Everything | Global audit, debug logging |

Subscriptions are stored in a module-level array and re-sorted by priority after every new subscription (`bus.ts:42`). The sort is stable -- subscriptions at the same priority preserve insertion order.

**Unsubscribe:** `subscribe()` returns a zero-arg function. Calling it removes the subscription from the registry by reference (`bus.ts:46-51`). This is critical for teardown in tests and hot-reload scenarios.

**Utilities:**
- `subscriptionCount()` (`bus.ts:143-145`) -- returns active subscription count.
- `clearSubscriptions()` (`bus.ts:150-152`) -- removes all subscriptions. Used in test teardown.

### Acceptance Criteria

- [ ] `subscribe("guest.*", handler)` matches `guest.created`, `guest.updated`, `guest.deleted` but not `schedule.created`.
- [ ] `subscribe("*.created", handler)` matches `guest.created`, `schedule.created` but not `guest.updated`.
- [ ] `subscribe("*", handler)` matches every event.
- [ ] Exact match `guest.created` does not match `guest.created.extra` (segment count mismatch).
- [ ] Calling the returned unsubscribe function removes only that subscription.
- [ ] After unsubscribe, `subscriptionCount()` decrements by 1.
- [ ] Subscriptions with priority 10 execute before priority 100.
- [ ] Two subscriptions at the same priority execute in insertion order.

## 3. Emission Model

### Purpose

Dispatch a domain event to all matching handlers sequentially, isolate errors, and return a complete execution record.

### Detail

`emit()` (`bus.ts:61-118`) does the following in order:

1. **Log intent** -- structured log with `eventId`, `recordId`, `triggeredBy`.
2. **Filter** -- find all subscriptions whose pattern matches `event.eventName` via `matchesPattern()`.
3. **Execute sequentially** -- iterate matching subscriptions (already sorted by priority). For each:
   - Call `handler(event)` and await.
   - On success: push `{ workflowName: pattern, actionType: "handler", success: true }`.
   - On failure: catch, log error, push `{ workflowName: pattern, actionType: "handler", success: false, error: message }`. **Execution continues.**
4. **Build EventLogEntry** -- assemble `eventId`, `eventName`, `recordId`, `triggeredBy`, `timestamp`, `workflowsTriggered` (list of matched patterns), `actionsExecuted` (success/failure per handler).
5. **Log to Postgres** -- fire-and-forget write to `event_log` table (non-blocking; failure is warned, not thrown).
6. **Return** the `EventLogEntry` to the caller.

**Error isolation** is the key design constraint: a failing handler must never prevent subsequent handlers from running, and must never cause `emit()` itself to throw.

**Pattern matching** (`bus.ts:167-180`):
- `"*"` alone matches everything (early return).
- Otherwise, split both pattern and event name on `.`. If segment counts differ, no match. Each segment must be `"*"` or an exact string match.

### Acceptance Criteria

- [ ] `emit()` returns an `EventLogEntry` even when all handlers fail.
- [ ] A handler throwing an error does not prevent subsequent handlers from executing.
- [ ] `actionsExecuted` contains one entry per matched handler, with correct `success` and `error` fields.
- [ ] `workflowsTriggered` lists every matched subscription pattern.
- [ ] `emit()` never throws -- all internal errors are caught and logged.
- [ ] Handlers execute in priority order (verified by checking `actionsExecuted` array order).

## 4. Event Logging

### Purpose

Maintain a complete, queryable audit trail of every domain event and its execution results. Postgres is the system of record.

### Detail

Every `emit()` call writes an `EventLogEntry` to the `event_log` table in Postgres. The write is fire-and-forget (non-blocking) so event processing latency is not affected by logging speed.

**`event_log` table schema:**

| Column | Type | Description |
|--------|------|-------------|
| `event_id` | `uuid` PRIMARY KEY | From `DomainEvent.eventId` |
| `event_name` | `text` NOT NULL | e.g. `guest.created` |
| `record_id` | `text` NOT NULL | Postgres row ID of affected record |
| `triggered_by` | `text` NOT NULL | User email or `"system"` |
| `timestamp` | `timestamptz` NOT NULL | Event creation time |
| `workflows_triggered` | `text[]` | Array of matched subscription patterns |
| `actions_executed` | `jsonb` NOT NULL | Array of `{ workflowName, actionType, success, error? }` |
| `created_at` | `timestamptz` DEFAULT `now()` | Row insertion time |

**Current state (bus.ts:113-116):** The existing code writes to an external store via a legacy logging function. This is replaced with a direct Postgres insert to the `event_log` table via `logEventToPostgres()`.

**Implementation steps:**
1. Create `event_log` table in Postgres schema migration.
2. Implement `logEventToPostgres()` using a parameterized INSERT, replacing the legacy logger.
3. Add index on `event_name` and `timestamp` for query performance.
4. Add index on `record_id` for per-record audit trail lookups.

**Querying:** The event log supports:
- Per-record audit trail: `SELECT * FROM event_log WHERE record_id = $1 ORDER BY timestamp`.
- Failed-action diagnostics: `SELECT * FROM event_log WHERE actions_executed @> '[{"success": false}]'`.
- Event frequency: `SELECT event_name, count(*) FROM event_log GROUP BY event_name`.

### Acceptance Criteria

- [ ] Every `emit()` call produces a row in `event_log`.
- [ ] Logging failure does not cause `emit()` to throw.
- [ ] `actions_executed` JSONB accurately reflects handler success/failure with error messages.
- [ ] `event_log` has indexes on `event_name`, `record_id`, and `timestamp`.
- [ ] Log entries are queryable for per-record audit trails within 1 second for tables with up to 1M events.

## 5. Scaling Path

### Purpose

Define the migration from in-process event bus to distributed event delivery without breaking existing handlers.

### Detail

**Phase A -- In-process (current):**
All handlers run inside the same Cloud Functions process. The module-level `subscriptions` array is the registry. This is correct for all internal platform logic (workflows, cascades, audit).

**Phase B -- Cloud Pub/Sub for external delivery:**
When external services or apps need to react to domain events:

1. Add a built-in handler (priority 999, always last) that publishes every event to a Pub/Sub topic named `domain-events`.
2. External consumers subscribe to the Pub/Sub topic with server-side filtering on `attributes.eventName`.
3. Internal handlers stay in-process. No changes to existing `subscribe()` calls.
4. Pub/Sub delivery adds at-least-once semantics. External consumers must be idempotent (keyed on `eventId`).

**Phase C -- Cross-service (future):**
If the platform splits into multiple Cloud Run services:
1. Replace the in-process bus with Pub/Sub as the primary transport.
2. Each service subscribes to relevant topics/filters.
3. `subscribe()` API stays the same -- the implementation behind it changes from array iteration to Pub/Sub subscription management.

**Design constraint:** The `subscribe()` / `emit()` API surface never changes. Scaling is an implementation detail behind the same interface.

### Acceptance Criteria

- [ ] In-process handlers continue working with zero changes when Pub/Sub bridge is added.
- [ ] Pub/Sub bridge handler runs at priority 999 (after all internal handlers).
- [ ] External consumers receive events with full `DomainEvent` payload as Pub/Sub message data.
- [ ] External consumers can filter by `eventName` attribute without receiving all events.
- [ ] `eventId` is available as a Pub/Sub attribute for deduplication.

## 6. Event Patterns

### Purpose

Define the standard event patterns used across the platform so that all modules emit events consistently.

### Detail

**Lifecycle events** -- fired by the data access layer on every write:

| Event | When | changedFields | previousValues/newValues |
|-------|------|---------------|--------------------------|
| `{concept}.created` | Row inserted | All fields | newValues only |
| `{concept}.updated` | Row updated | Changed fields only | Both previous and new |
| `{concept}.deleted` | Row soft-deleted | `["status"]` | `{ status: "deleted" }` |

**Status transition events** -- fired when a status field changes:

| Event | Example | Payload |
|-------|---------|---------|
| `{concept}.completed` | `task.completed` | previousValues: `{ status: "active" }`, newValues: `{ status: "completed" }` |
| `{concept}.overdue` | `task.overdue` | Triggered by scheduled check |
| `{concept}.staffing_complete` | `event.staffing_complete` | All staff slots filled |

**External sync events** -- fired when data arrives from an integration:

| Event | When |
|-------|------|
| `{concept}.external_created` | Integration creates a record |
| `{concept}.external_updated` | Integration updates a record |
| `{concept}.synced` | Bidirectional sync completed |
| `{concept}.intake_received` | Form submission or external intake |

**Cascade patterns** -- one event triggers another:
- `guest.created` handler assigns default schedule -> fires `schedule.updated`.
- `convention.updated` (date change) handler updates all linked events -> fires N x `event.updated`.
- Cascades are natural (handler calls `emit()` internally). No special cascade mechanism needed. Depth is bounded by domain logic, not bus configuration.

**Scheduled events** -- fired by Cloud Scheduler / cron:
- `task.overdue` -- daily check for tasks past due date.
- `convention.reminder` -- pre-convention notification windows.
- Scheduled jobs call `emit()` with `triggeredBy: "system"`.

### Acceptance Criteria

- [ ] Every Postgres INSERT fires `{concept}.created`. Every UPDATE fires `{concept}.updated`. Every soft-delete fires `{concept}.deleted`.
- [ ] Status transitions fire the specific action event (`completed`, `overdue`, etc.) in addition to `updated`.
- [ ] External sync events use the `external_*` / `synced` / `intake_received` actions, not `created`/`updated`.
- [ ] Cascaded events carry their own `eventId` and `timestamp` (they are independent events, not children).
- [ ] Scheduled events set `triggeredBy` to `"system"`.

## 7. Test Plan

### Purpose

Verify every behavior of the event bus in isolation and integration, from pattern matching to concurrent load.

### Detail

**7a. Pattern matching unit tests:**

| Test | Input | Expected |
|------|-------|----------|
| Exact match | pattern `guest.created`, event `guest.created` | match |
| Concept wildcard | pattern `guest.*`, event `guest.updated` | match |
| Action wildcard | pattern `*.created`, event `schedule.created` | match |
| Global wildcard | pattern `*`, event `anything.here` | match |
| Segment mismatch | pattern `guest.*`, event `guest.created.extra` | no match |
| No match | pattern `guest.created`, event `guest.updated` | no match |
| Multi-segment wildcard | pattern `*.*.created`, event `org.guest.created` | match |

**7b. Priority ordering tests:**

| Test | Setup | Expected |
|------|-------|----------|
| Lower priority first | Subscribe at 10 and 100, emit | Priority-10 handler's side-effect appears first |
| Equal priority | Subscribe A then B at default 100, emit | A executes before B |
| Re-sort on subscribe | Subscribe at 100, then at 10 | New subscription at 10 is first in execution order |

**7c. Error isolation tests:**

| Test | Setup | Expected |
|------|-------|----------|
| Failing handler | Handler 1 throws, handler 2 succeeds | Both appear in `actionsExecuted`; handler 2 runs |
| All handlers fail | Both handlers throw | `emit()` returns log entry with two failures, does not throw |
| Error message capture | Handler throws `new Error("bad")` | `actionsExecuted[n].error === "bad"` |

**7d. Emit-to-log integration tests:**

| Test | Setup | Expected |
|------|-------|----------|
| Log written | Emit event, query `event_log` | Row exists with correct `event_id`, `event_name`, `record_id` |
| Workflows recorded | Emit with 3 matching subscriptions | `workflows_triggered` contains 3 patterns |
| Actions recorded | Emit with 1 success, 1 failure | `actions_executed` JSONB has both with correct `success` values |
| Log failure tolerated | Mock Postgres insert to throw | `emit()` still returns normally |

**7e. Subscribe/unsubscribe tests:**

| Test | Setup | Expected |
|------|-------|----------|
| Unsubscribe removes handler | Subscribe, unsubscribe, emit | Handler not called; `subscriptionCount()` is 0 |
| clearSubscriptions | Subscribe 3, clear | `subscriptionCount()` is 0 |
| Double unsubscribe | Call unsubscribe twice | No error, no side effects |

**7f. Concurrent emission load tests:**

| Test | Setup | Expected |
|------|-------|----------|
| 100 concurrent emits | `Promise.all()` with 100 `emit()` calls | All 100 return valid `EventLogEntry`; no handler interleaving within a single emit |
| Handler with async delay | Handler sleeps 50ms, 50 concurrent emits | All complete; total time ~50ms (parallelism across emits) |
| Subscription mutation during emit | Add subscription mid-emit | Current emit uses snapshot; new subscription active on next emit |

### Acceptance Criteria

- [ ] All pattern matching tests pass (7a).
- [ ] Priority ordering is deterministic and verified by execution trace (7b).
- [ ] Error isolation is verified: failing handlers never block subsequent handlers or cause `emit()` to throw (7c).
- [ ] Integration tests confirm event_log rows match emitted events (7d).
- [ ] Unsubscribe and clearSubscriptions behave correctly (7e).
- [ ] Load tests confirm no handler interleaving within a single `emit()` call (7f).
- [ ] All tests run in under 5 seconds total (excluding load tests).
